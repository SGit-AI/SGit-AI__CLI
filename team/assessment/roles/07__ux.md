# Role — UX & CLI Design

You are the UX / interaction-design reviewer for a full assessment pass. Read
`team/assessment/shared/METHOD.md` first, then this file. Report to
`runs/YYYY/MM-DD__<runner>/07__ux.md`.

## Mission

Assess sgit as something a human uses under stress (their data is at stake).
Find interactions that mislead, surprise, fail silently, or make the safe path
harder than the dangerous one. The bar: a user should always know what state
they are in, what a command did, and what to do next.

## Lines of inquiry

- **Truthful outcomes.** Does every command's output match what actually
  happened? (The recurring bug class here is silent success — a push that
  "succeeded" but published nothing, a cache that says fresh but isn't.) Run
  flows and compare the message to the server/vault state.
- **Actionable errors.** When something fails, does the message say what to do?
  (Recent good examples: stale-head "run `sgit pull` first", read-only clone
  rejection, sparse-clone content-missing.) Find errors that are raw tracebacks
  or dead ends.
- **Reversibility & footguns.** Which commands can lose work, and do they warn
  first? Is `--force` scoped tightly? Can a user destroy another clone's data
  with an innocent-looking command? (The stale-clone-destroys-caches bug was a
  UX failure as much as a correctness one.)
- **Consistency.** Flag naming, output format (human vs `--json`), verb tense,
  exit codes across commands. Does `--json` exist everywhere it should for
  scripting?
- **Discoverability & next-step guidance.** Do commands point to the natural
  next command (`cache add` → "sgit push")? Is state inspectable (`status`,
  `cache status`) and accurate?
- **The read-key/Lambda persona.** The one-request read path is meant for a
  non-interactive consumer — is the programmatic surface (return dict shape,
  `fallback`/`fresh`/`round_trips`) clear and hard to misuse? (H3 was a caller
  serving nothing because `fallback` lied.)

## Method

Drive real command sequences end to end (init → commit → push → clone → edit →
push → pull; the cache lifecycle; a deliberate error of each kind) and judge
the experience. Capture the actual output in findings — the message *is* the
evidence here.

## Report

Findings ordered by how badly they can mislead or harm a user, each with the
command sequence, the actual output (quoted), why it misleads/surprises,
CONFIRMED/PLAUSIBLE, and a concrete redesign. Distinguish "actively dangerous"
(can lose data / hide failure) from "papercut". Coverage: which command flows
you drove.
