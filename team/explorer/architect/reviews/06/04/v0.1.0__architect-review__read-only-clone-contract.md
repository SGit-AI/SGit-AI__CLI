## 1. Executive Summary

A read-only clone is a vault directory where the user holds the **read key but not the write key** and has cloned the **server's named-branch HEAD** (typically `current`) directly into the working copy with no local clone branch on top. Every read-side subcommand inside the directory has to derive keys from `clone_mode.json` instead of `vault_key`, and read the HEAD commit from the named-branch ref instead of a synthetic clone-branch ref.

The bug surface is three-fold:

1. **Key derivation.** `Step__Pull__Derive_Keys` and `Step__Fetch__Derive_Keys` call `_read_vault_key(directory)` which assumes a passphrase file exists. A read-only clone deliberately omits it (correctly — the user does not have one).
2. **Local-config read.** Every read action eventually calls `_read_local_config`, which assumes `.sg_vault/local/config.json` exists and contains a clone-branch ID. A read-only clone has neither today.
3. **Pull algorithm shape.** `Vault__Sync__Pull` is structurally a clone-branch ↔ named-branch merge. A read-only clone has no clone branch; merge is undefined.

The fix is **one shared helper** that initialises the directory using the same clone-mode dispatch already present at `Vault__Sync__Base._init_components` (lines 64-85), plus a **synthetic-config policy** so the local-config read returns a deterministic object even when `config.json` is absent. The fix preserves zero-knowledge (no new server interactions, no new metadata on disk), preserves the byte-for-byte crypto contract (uses the existing `import_read_key`), and is backwards-compatible with the user's existing `/tmp/pmcv9tfe` clone.

**Severity verdict:**
- The four crash bugs are **HIGH** (visible, every read-side subcommand affected on every read-only clone).
- The storage-layout decision about whether to start writing `config.json` for RO clones is **MEDIUM** (open question, see §4 and §10).
- The pull algorithm is **MEDIUM** (already gated at CLI level by commit `2b9f4f5`; this contract upgrades the gate to a structural redefinition).

## 3. Storage Layout — Read-Only Clone (Normative)

### 3.1 The two on-disk regimes

| Regime | Description | When written |
|---|---|---|
| **Regime A — RO-minimal** (current, the user's `/tmp/pmcv9tfe` is in this regime) | Only `clone_mode.json` lives in `.sg_vault/local/`. Plus all the `.sg_vault/bare/*` content from the named branch HEAD. | Produced by `Step__Clone__ReadOnly__Setup_Config` in v0.14.x and earlier. |
| **Regime B — RO-with-config** (new, defined by this contract) | Adds a `config.json` with a fixed shape (see §3.3). All other on-disk content is identical to Regime A. | Produced by a follow-up Dev change in `Step__Clone__ReadOnly__Setup_Config`. |

Both regimes MUST be supported by the read paths for backwards compatibility (see §6). The new clone path SHOULD produce Regime B going forward.

### 3.2 Complete file inventory for an RO clone (Regime B)

```
<directory>/
├── .sg_vault/
│   ├── bare/
│   │   ├── data/           ← all commit, tree, and blob objects reachable from named-branch HEAD
│   │   ├── refs/<named_ref_id>          ← the named branch's HEAD ref (encrypted commit pointer)
│   │   ├── keys/<public_key_id>         ← named-branch signing public key
│   │   ├── indexes/<branch_index_file_id> ← branch index (encrypted)
│   │   ├── branches/       ← empty in RO clones (no clone branch lives here)
│   │   └── pending/        ← empty in RO clones
│   └── local/
│       ├── clone_mode.json                ← ALWAYS PRESENT in RO clones; see §3.4
│       └── config.json                    ← NEW (Regime B); see §3.3
└── (working-copy files, decrypted from named-branch HEAD)
```

**MUST NOT exist** in an RO clone (any regime):

- `local/vault_key` — the user does not hold the passphrase. Writing one here would be incoherent.
- `local/token` and `local/base_url` — RO clones use the default API base URL and no auth token for the read path (the existence-of-vault check is unauthenticated by current API contract). Tokens MAY be added later if the user runs `sgit vault remote add` against the RO clone (out of scope here).
- Any clone-branch ref or clone-branch metadata. RO clones have **no clone branch**.

### 3.3 `Schema__Local_Config` extension for Regime B (normative)

The schema needs one new field to encode the regime. Today `Schema__Local_Config` has four fields:

```python
class Schema__Local_Config(Type_Safe):
    my_branch_id : Safe_Str__Branch_Id       = None
    mode         : Enum__Local_Config_Mode   = None
    edit_token   : Safe_Str__Simple_Token    = None
    sparse       : bool                      = False                          # CLAUDE.md violation — see Finding F7
```

Proposed Regime-B shape (the schema is extended, not replaced — full clones unaffected):

```python
class Enum__Local_Config_Mode(Enum):
    SIMPLE_TOKEN = 'simple_token'
    READ_ONLY    = 'read_only'      # NEW

class Schema__Local_Config(Type_Safe):
    my_branch_id : Safe_Str__Branch_Id     = None              # None on RO clones (no clone branch)
    mode         : Enum__Local_Config_Mode = None              # READ_ONLY for RO clones
    edit_token   : Safe_Str__Simple_Token  = None              # None on RO clones
    sparse       : bool                    = False             # Carried through from clone-time --sparse flag
```

**Open question Q1 — Boolean field, no Safe_Bool.** The existing `sparse: bool = False` field is itself a CLAUDE.md violation (raw `bool` primitive plus a mutable default `False`). The team has been carrying it for a while. This contract MUST NOT make it worse; the RO addition only introduces an `Enum__Local_Config_Mode` member, which is rule-compliant. Fixing `sparse` to be `Safe_Bool`-backed is out of scope for this fix and is tracked in the May review. **Decision deferred to Dinis** — see §10 Q1.

Round-trip invariant remains:
```python
assert Schema__Local_Config.from_json(obj.json()).json() == obj.json()
```

### 3.4 `Schema__Clone_Mode` — already correct

No changes. The existing shape is sufficient:

```python
class Schema__Clone_Mode(Type_Safe):
    mode     : Enum__Clone_Mode    = None      # READ_ONLY | FULL
    vault_id : Safe_Str__Vault_Id  = None
    read_key : Safe_Str__Write_Key = None      # 64-hex AES-256 key
```

### 3.5 Where does HEAD live?

In Regime A and B, the named branch's encrypted HEAD ref is at `.sg_vault/bare/refs/<named_ref_id>` — written during `Step__Clone__Download_Branch_Meta`. There is **no clone-branch ref** in either regime. Therefore the contract for "the HEAD of an RO clone" is:

> The HEAD of an RO clone is the last-fetched value of the named branch's `<named_ref_id>`, decrypted with the read_key.

This is byte-identical to what `Vault__Sync__Pull.Step__Pull__Fetch_Remote_Ref` already does for full clones; the read-only adaptation is to use the same logic but skip the merge.

### 3.6 Zero-knowledge audit

| Observation | Verdict |
|---|---|
| RO clone writes only `clone_mode.json` (or +`config.json`) to local | No server interaction; nothing leaves the device. |
| Reading the named-branch ref from the server already happens for every full clone today | Not a new leak. The vault_id is observable to the server during any read. |
| Storing `clone_mode.json` plaintext (containing `read_key`) | Documented accepted risk (Dinis decision; AppSec F07 — see `Schema__Clone_Mode.py:8-10`). Not changed by this contract. |
| Storing `config.json` plaintext (containing `mode = READ_ONLY` literal) | New: the literal string `'read_only'` is added to disk. This leaks **nothing** beyond what `clone_mode.json` already declares. No new leak vector. |

**Verdict:** the storage layout proposed here is zero-knowledge-neutral.

## 4. Key-Derivation Contract (Normative)

### 4.1 The shared helper

Add **one** clone-mode-aware key-derivation method on `Vault__Sync__Base`. Every `Step__*__Derive_Keys` and every read action's `_init_components` call routes through it. No more divergent paths.

Proposed signature (Type_Safe class method on `Vault__Sync__Base`):

```python
def _derive_keys_for_directory(self, directory: str) -> dict:
    """Return a uniform keys dict for the directory, regardless of clone mode.

    Returns dict matching the shape produced by:
      - crypto.derive_keys_from_vault_key()       (full / headless / simple-token clones)
      - crypto.import_read_key()                  (read-only clones)

    Both shapes already expose the union keys:
        vault_id, read_key, read_key_bytes,
        ref_file_id, branch_index_file_id,
        write_key  (str — '' on RO), write_key_bytes (bytes|None — None on RO)
    """
```

**Algorithm (pseudocode, normative):**

```
storage = Vault__Storage()
clone_mode_path = storage.clone_mode_path(directory)

if os.path.isfile(clone_mode_path):
    raw = json.load(open(clone_mode_path))
    schema = Schema__Clone_Mode.from_json(raw)
    if schema.mode == Enum__Clone_Mode.READ_ONLY:
        if not schema.read_key or not schema.vault_id:
            raise Vault__Clone_Mode_Corrupt_Error()
        return self.crypto.import_read_key(str(schema.read_key), str(schema.vault_id))

# Fall through: full clone or pre-v0.14 vault
vault_key = self._read_vault_key(directory)
return self._derive_keys_from_stored_key(vault_key)
```

This is **byte-identical** to the dispatch already living inside `_init_components` at `Vault__Sync__Base.py:64-84`. The new helper extracts that dispatch into a callable so that `Step__Pull__Derive_Keys` and `Step__Fetch__Derive_Keys` can use it without duplicating the logic.

### 4.2 Required call-site changes (binding for Dev)

| Call site | Today | Required behaviour |
|---|---|---|
| `Step__Pull__Derive_Keys.execute` line 25-26 | `vault_key = _read_vault_key(directory); keys = _derive_keys_from_stored_key(vault_key)` | `keys = self.workspace.sync_client._derive_keys_for_directory(directory)` |
| `Step__Fetch__Derive_Keys.execute` line 25-26 | same | same |
| `Vault__Sync__Base._init_components` lines 79-84 | inline dispatch | DELEGATE to `_derive_keys_for_directory(directory)`. Single source of truth. |

The dispatch logic ends up living in ONE place. Today it lives in two (`_init_components` and the two derive-keys steps). The contract says: ONE.

### 4.3 Why not extend `_derive_keys_from_stored_key`?

Considered and rejected. `_derive_keys_from_stored_key(vault_key)` takes a passphrase argument. An RO clone has no passphrase. Reshaping the method to take a directory would change the function's domain — too invasive. The helper `_derive_keys_for_directory` is purpose-built for the dispatch.

### 4.4 Crypto interop

No new crypto operations are introduced. `import_read_key` and `derive_keys_from_vault_key` are existing, tested, and Web-Crypto-equivalent (per `tests/unit/crypto/`). The contract uses them as-is. **No new test vectors required.**

## 5. Per-Subcommand Semantics in a Read-Only Clone (Normative)

This table is binding for Dev. Every read-side command is enumerated.

### 5.1 The synthetic-config policy

To make read paths uniform, the read-only path SHALL synthesize a `Schema__Local_Config` when `config.json` is absent (Regime A — backwards compatibility). The synthesis is:

```python
Schema__Local_Config(
    my_branch_id = None,                                  # No clone branch — sentinel
    mode         = Enum__Local_Config_Mode.READ_ONLY,
    edit_token   = None,
    sparse       = False,                                 # Best-effort; Regime A doesn't preserve --sparse
)
```

The mechanism is a new helper on `Vault__Sync__Base`:

```python
def _read_local_config_or_default(self, directory: str, storage: Vault__Storage) -> Schema__Local_Config:
    """Like _read_local_config, but synthesises a READ_ONLY shape when config.json is absent
    AND clone_mode.json declares READ_ONLY. Otherwise re-raises FileNotFoundError as today
    (so full clones still surface a corrupt-state error early)."""
```

`_read_local_config` itself MUST remain unchanged. Read sites that need to tolerate RO call the new helper. Write sites continue to use the strict reader.

### 5.2 Subcommand contract table

- **Works?** YES / REFUSE / DEGRADED
- **HEAD source** = where the command resolves the current commit
- **Network?** = whether the command may issue API calls

### 5.3 The new `pull` semantics on RO (normative)

The current `Workflow__Pull` does five steps: derive_keys → load_branch_info → fetch_remote_ref → fetch_missing → merge.

On a read-only clone this becomes a four-step workflow with **no merge**:

```
Workflow__Pull__ReadOnly (NEW):
    Step__Pull__Derive_Keys              (same code, now clone-mode-aware via §4.1)
    Step__Pull__RO__Load_Named_Head      (NEW — fetches named-branch HEAD, no clone-branch lookup)
    Step__Pull__Fetch_Missing            (reuses existing, with stop_at = previously-cached named-HEAD)
    Step__Pull__RO__Checkout             (NEW — writes the new HEAD's tree into the working copy; no merge)
```

The dispatch lives in `cmd_pull`:

```
if clone_mode is READ_ONLY:
    run Workflow__Pull__ReadOnly
else:
    run Workflow__Pull                    (the existing 5-step)
```

This is a **structural** fix that replaces the early-exit gate added in commit `2b9f4f5`. The gate stays as the safety net until the new workflow lands.

**Open question Q2 — `pull` semantics: redefine or refuse?** Confirming `redefine` is correct, but there is a UX subtlety: the user who runs `sgit pull` on an RO clone today expects a refuse-with-hint (commit `2b9f4f5`). **Tradeoff:** redefine = git-like (`pull` always brings in remote changes); refuse = makes the read/write boundary loud and forces an explicit verb. **Recommendation:** redefine. **Decision deferred to Dinis** — see §10 Q2.

## 6. Migration / Backwards Compatibility (Normative)

### 6.1 Compatibility requirement

**Existing RO clones MUST keep working without re-cloning.** `/tmp/pmcv9tfe`, cloned with v0.14.24 (Regime A — only `clone_mode.json`), MUST run `sgit ls`, `cat`, `fetch`, `pull`, `status`, `log`, `branches`, `info`, `diff` after upgrade.

### 6.2 The compatibility mechanism

Read paths invoke `_read_local_config_or_default`. When the RO clone is in Regime A (`config.json` absent + `clone_mode.json` declares `READ_ONLY`), the helper synthesises a `Schema__Local_Config` matching the Regime-B shape. Read commands proceed as if the config existed.

**Read paths MUST tolerate `my_branch_id is None`** and fall back to the named branch via `get_branch_by_name(branch_index, 'current')`.

### 6.3 Upgrade hook (optional, recommended)

On first run inside a Regime-A RO clone, the CLI MAY transparently materialise `config.json` (upgrading the directory in-place to Regime B). OPTIONAL — the read paths work either way. **Open question Q3** — implement now or defer. **Recommendation:** defer.

### 6.4 What we DON'T require

- `vault_key` file is NEVER materialised on an RO clone. To upgrade to read-write: re-clone as a full clone.
- No version-bump or schema-version field on `Schema__Local_Config`. The presence/absence of `mode = READ_ONLY` is the in-band signal.

| Rule | Rationale |
|---|---|
| 1. **DO NOT** modify `_read_local_config`. Add `_read_local_config_or_default` as a sibling. | The strict reader is a safety net for full clones. |

| 3. **DO NOT** invent a synthetic "clone branch ID" for RO clones. `my_branch_id` MUST be `None`. | A fake branch ID could corrupt the branch index on re-clone. |
| 4. **DO NOT** create a clone-branch ref or branch metadata in the bare store on RO clones. | RO clones have NO clone branch. |
| 5. **DO NOT** call `_derive_keys_from_stored_key(vault_key)` from any RO code path. | It takes a passphrase. Use `_derive_keys_for_directory(directory)`. |
| 6. **DO NOT** add network calls to the read paths beyond what already exists. | Expands the zero-knowledge audit surface; needs separate Architect review. |
| 7. **DO NOT** add Pydantic, raw `dict` fields, or `@staticmethod`. Use Type_Safe + Safe_* types. | CLAUDE.md hard requirement. |
| 8. **DO NOT** remove the early `cmd_pull` RO gate (commit `2b9f4f5`) until `Workflow__Pull__ReadOnly` is wired in and integration-tested. | The gate is the current safety net. Replace, don't delete. |
| 9. **DO NOT** change the byte format of `clone_mode.json` or `config.json` such that existing files become unparseable. | Backwards compatibility (§6 binding). |
| 10. **DO NOT** add `Enum__Local_Config_Mode.READ_ONLY` to SIMPLE_TOKEN code paths. Modes are mutually exclusive. | Keep mode dispatch flat. |
| 11. **DO NOT** write `.sg_vault/local/token` or `.sg_vault/local/base_url` from the RO clone setup step. | Token storage belongs to the remote-config contract, not this one. |
| 12. **DO NOT** consolidate the `Step__*__Derive_Keys` classes into one shared class. | They serve different state schemas; keep step granularity. |
