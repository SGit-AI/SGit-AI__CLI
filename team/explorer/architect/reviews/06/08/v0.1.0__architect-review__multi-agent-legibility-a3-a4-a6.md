## 1. Executive Summary

The commit is well-structured, all 20 new tests and 793 surrounding tests pass, no test `__init__.py` was added, and no module-level functions were introduced into production. The core read paths (`log`, `diff`, `show`, `resolve`, `merge`) are not regressed for the common (full-clone) case: plain `history log` with no flags still routes to `vault.cmd_log` (verified by `test_no_details_without_range_does_not_use_range_machinery`), and the A4 `--show` path and A3 on-demand fetch are read-only (no ref writes, no merge, no working-copy mutation, writes confined to `bare/data`).

However, there are two correctness gaps and one behavioural side-effect that should be fixed before this ships as the multi-agent answer:

1. **A3 does not work on a `READ_ONLY` clone** — the exact scenario it advertises. `Vault__Diff._init_components` (`Vault__Diff.py:552`) hard-reads `local/vault_key`, which a read-only clone deliberately does not have (per the 06/04 contract). On a read-only clone the on-demand fetch raises `FileNotFoundError(local/vault_key)`, is silently swallowed, and the user gets the old "run sgit pull" hint. The "read-only on-demand fetch" headline is only true for full/headless clones.
2. **A6 silently drops `-n/--limit`** — `history log --files -n 5` routes to `cmd_log_range`, which never reads `limit`. The user asks for the last 5 commits and gets the entire history. Same for `--graph` (ignored in details mode). This is a silent surprise on a core command.
3. **A3 introduces a new outbound-network trigger on previously-offline commands.** `history show`/`diff` can now fire a read call to the **default** API host even when no remote is configured (`resolve_remote` always returns a default `base_url`). Gated only on the error string `'bare/data'`, not on "a remote exists." Read-only and within the existing zero-knowledge envelope (vault_id is already server-observable on any read), but a previously-offline command can now reach the network.

The A4 verdict logic is sound, A3's read-only/`bare/data`-confinement guarantee holds, and the retry control flow is safe (the `result is None` JSON sentinel cannot collide with a real diff result, and uncaught retry exceptions are cleanly handled by the outer handler in `CLI__Main.run`).

**Verdict: FIX-THEN-SHIP.** No CRITICAL, no zero-knowledge violation, no crypto-interop impact. One HIGH (A3 read-only-clone gap — fix or scope the claim), one HIGH (A6 `-n` silent drop — fix or reject the flag). Three MEDIUM worth acting on now. The features are otherwise safe to ship.

## 3. Probe-by-Probe Confirmation

### Probe 1 — A3 read-only guarantee (no writes outside `bare/data`, no ref/merge/working-copy mutation)

**CONFIRMED read-only and `bare/data`-confined.** `ensure_commit_local` (`Vault__Diff.py:700-712`) calls `Vault__Sync__Pull._fetch_missing_objects` with `include_blobs=True`. That method:
- Reads only: `api.batch_read` (`Vault__Sync__Pull.py:259`), `api.read` (`:405`), `api.presigned_read_url`+`urlopen` for large blobs (`:402-403`). **No `api.write`, no ref/branch/index mutation, no merge call.**
- Writes only through the inner `_save` (`:248-253`), which hard-codes `os.path.join(sg_dir, 'bare', 'data', oid)`. It cannot write outside `bare/data` — the path is constructed from `sg_dir` + the literal `'bare'/'data'` + a content-address id (the `bare/data/` prefix is stripped). No ref file, no `local/`, no working copy is touched.

**Caveat (F1):** "is it safe on a read-only clone" — it is *safe* (no writes attempted) but *non-functional*: `_init_components` raises on `local/vault_key` before the puller runs. So the read-only-clone contract is not violated (nothing is written), but the feature does not deliver on read-only clones.

### Probe 2 — A3 unintended network / unbounded work

**Partially CONFIRMED — two concerns.**
- **Gating (F3):** fires on `'bare/data' in str(e)` + `vault_ref`/`token_store` wired. `token_store.resolve_remote` always returns a default `base_url` (`CLI__Token_Store.py:101-103`), so the api builds even with no configured remote → a previously-offline `history show`/`diff` can reach the default host. Failures are swallowed and fall back to the hint, so no crash, but a new network trigger. Recommend gating on a real remote (F3).
- **Unbounded ancestry (CONFIRMED, accept with caveat):** `ensure_commit_local` does **not** pass `stop_at`, so `_fetch_missing_objects` walks the **entire** ancestry of `commit_id` (BFS over all parents, `Vault__Sync__Pull.py:317`) and, with `include_blobs=True`, downloads all reachable commits + trees + blobs that are missing locally. On a fresh/sparse clone, a single `history show <tip>` can download the whole history. This is *functionally correct* (you need ancestors to diff `show`'s parent), and it converges (it skips objects already present), but it is unbounded. For the multi-agent "inspect one collaborator commit" use case this is heavier than necessary. Acceptable for v0.1.0 given the convergence, but worth a note: `show`/`diff` only strictly need the target commit, its parent(s), and their two trees + the differing blobs — not the full transitive history. A future bound (`stop_at` = nearest cached commit, or a depth limit) would make on-demand fetch proportional to the inspection. Not blocking; flag as a known characteristic.

### Probe 3 — A3 retry control flow

**CONFIRMED safe on all four sub-points.**
- (a) `result` always bound before use: in `cmd_diff`, `result = _compute()` (`:220`); on `FileNotFoundError`, either the retry rebinds `result` (`:226`) or `_exit_missing_object` calls `sys.exit` (`:228,230`); on `RuntimeError`, `sys.exit` (`:232-233`). The only fall-through to `if result is None` (`:235`) is the success path or the JSON-printed path → `result` is always bound. Same structure in `cmd_show`.
- (b) RuntimeError on the *retry* is not caught locally (inner `try` catches only `FileNotFoundError as e2`), but `CLI__Main.run:735` catches `RuntimeError` at the top → clean `error:` + exit 1, no traceback. Mitigated (F4).
- (c) `diff_vs_head/remote/commit` and `diff_commits` all `return self._build_result(...)` which returns a `Schema__Diff_Result` — **never `None`** (verified `Vault__Diff.py:40,48,56,65` + `_build_result:536`). The `result is None` sentinel (`:235`) is therefore exclusively the JSON-already-printed signal and cannot be misread for a real diff. No double-print (the JSON branch `return None` then `if result is None: return`).
- (d) `--remote`/HEAD modes (no commit ids): `targets = [c for c in (commit_id, commit_id2) if c]` is empty (`:222`), so `and targets` short-circuits → on-demand fetch never fires → behaviour unchanged. Confirmed.

### Probe 4 — A3 field additions / Type_Safe

**CONFIRMED no breakage.** `Vault__Diff.api : Vault__API = None` and `CLI__Diff.vault_ref/token_store : object = None` are optional with `None` defaults. All five non-test `Vault__Diff(crypto=...)` constructions still work; the 20 new tests construct both `Vault__Diff(crypto=...)` and `Vault__Diff(crypto=..., api=...)` and pass. Type_Safe accepts an optional Type_Safe-typed field (`Vault__API = None`) — verified empirically (green). The `object = None` typing for `vault_ref`/`token_store` mirrors the pre-existing pattern on `CLI__History` (`vault/diff/revert : object = None`) and `CLI__Merge.vault : object = None` — consistent with neighbouring code, avoids a circular import on `CLI__Vault`.

### Probe 5 — A6 dispatch regressions

**Mostly CONFIRMED clean; one silent surprise (F2).**
- Plain `history log` (no flags, no range): routes to `vault.cmd_log` — **byte-for-byte unchanged**, verified by `test_no_details_without_range_does_not_use_range_machinery`.
- `--files`/`--patch`/`--json` without range → `cmd_log_range` (full history). Works (`test_files_without_range_lists_all_commit_files`, `test_json_without_range_emits_structured_full_history`).
- **`-n/--limit` IS silently ignored (F2)** — `cmd_log_range`/`log_range_with_details` never read `limit`. `history log --files -n 5` returns full history.
- **`--graph` IS ignored in details mode** — `cmd_log_range` has no graph rendering; `--graph --files` silently drops the graph. (Plain `--graph` still routes to `vault.cmd_log`.)
- `--file <path>` combined with `--files`: `_dispatch_log` checks `file_path` **before** `wants_details` (`:32-35` and `:38-39`), so `--file` wins and routes to `cmd_log_file`. The `--files` flag is ignored in that case. Defensible precedence, but undocumented; worth a one-line help note.
- Positional-directory branch (`elif range_spec:` where range_spec is a path, `:27-37`): now also honours `wants_details` (`:34`) routing to `cmd_log_range` with the directory reassigned. Correct.

### Probe 6 — A4 correctness + safety

**CONFIRMED correct and read-only.**
- **Verdict logic is sound.** `three_way_conflict_view` (`Vault__Diff.py:617-664`) computes `ours_changed = ours_bid != base_bid`, `theirs_changed = theirs_bid != base_bid` on blob-ids from the flattened trees (`_commit_blob_map` uses `Vault__Sub_Tree.flatten`, no decryption for the map). This **matches the merge engine's own classification** (`Vault__Merge.py:35-36` uses the identical `ours_bid != base_bid` test). Cross-checked against every branch in `three_way_merge` that appends to `conflicts`:
  - both-in-base, both-changed, different blob (`:47-49`) → A4 `genuine` ✓
  - add/add different (`:57-59`, base absent) → both "changed" vs `None`, different → A4 `genuine` ✓
  - modify/delete (`:64-66`) and delete/modify (`:67-69`) → A4 labels `genuine` (one side's bid is `None`, the other changed, bids differ) — defensible (it IS a genuine conflict); the rendered diff shows the deleted side as empty. Not mislabelled as SUSPECT.
  So the only way a conflict gets a `one-sided`/`no-change` (SUSPECT) verdict is if the persisted `lca_id` differs from the LCA the engine actually used — precisely the stale-merge-base diagnostic the feature intends. Logic is correct.
- **Read-only display CONFIRMED.** `_show_conflicts` (`CLI__Merge.py:64-91`) only calls `Vault__Merge__State().read` and `three_way_conflict_view` (both pure reads) and `resolver.show` (verified read-only: `Vault__Merge__Resolve.show` only reads state + prints, `Vault__Merge__Resolve.py:63-77`). **No merge-state write, no `.conflict` file mutation, no working-copy change.**
- **Fallback CONFIRMED to catch the realistic failure.** The `try/except Exception` around `three_way_conflict_view` (`:79-90`) catches a missing-base read failure (`flatten`/`load_commit`/`load_tree` raise on a sparse clone where `lca_id`'s objects aren't local) and prints `(3-way view unavailable — …; showing paths only)` then `resolver.show`. The `except Exception` is broad enough to catch `FileNotFoundError`, `RuntimeError`, `KeyError`, decode errors — so it will not crash on a sparse/missing-base clone; it degrades to the path list. The only un-caught path is `Vault__Merge__State().read` itself raising before the `try` (`:71`), which is a genuinely corrupt merge-state (acceptable to surface). **Not tested** (F5).

### Probe 7 — Type_Safe / project conventions

**CONFIRMED compliant.**
- No module-level functions added to production (`git show 06b48ae -- sgit_ai/**` has zero `+def ` at column 0). `_is_range_spec` in `CLI__History` is pre-existing; `looks_like_range`/`parse_commit_range` in `_helpers` are pre-existing.
- No `@staticmethod` added. All new behaviour is methods on `CLI__Diff`/`CLI__Merge`/`Vault__Diff` (Type_Safe classes).
- New fields use immutable `None` defaults (`api : Vault__API = None`, `vault_ref/token_store : object = None`); no mutable default. `_VERDICT_LABELS` is a class-level dict literal of constant strings used as a lookup table (not a Type_Safe data field) — consistent with neighbouring constant tables (e.g. status-symbol dict at `CLI__Diff.py:146`); acceptable.
- **The new methods return plain `dict`/`list` of dicts** (`three_way_conflict_view → list[dict]`, `_commit_blob_map → dict`, `show_commit → tuple`, `commit_info → dict`). This is **consistent with the surrounding `Vault__Diff` code**, which already returns plain dicts from `show_commit`, `log_file`, `_flatten_commit`, `_read_head_files`, etc. These are internal method return values consumed immediately by the CLI printer — not persisted schemas, not Type_Safe data classes crossing a storage/API boundary. The CLAUDE.md "zero raw primitives" rule targets Type_Safe **schema fields**; internal dict returns are a pre-existing, accepted pattern in this module. **Not a new violation.** (A stricter future refactor could introduce a `Schema__Conflict_Row` Type_Safe class, but that is a separate hygiene item, not a regression.)

## 4. Zero-Knowledge & Crypto Interop

- **No new crypto operations.** A3 reuses `_fetch_missing_objects` (existing `api.read`/`batch_read` + `crypto.decrypt`/`decrypt_metadata`). A4 reuses `Vault__Sub_Tree.flatten` + `crypto.decrypt`. No new algorithm, no new key derivation, no test vectors required.
- **No new leak vector.** The only new server interaction is A3's on-demand read, which sends the same `vault_id` + content-address object ids already sent by `pull`/`fetch`. No file names, branch names, or plaintext leave the device. F3 is a new *trigger* for an existing-envelope observation (vault_id on a read), not a new *channel*. **Zero-knowledge guarantee preserved.**
- A4 writes nothing to the server and nothing to disk.

## 5. Open Questions (need human / cross-role input)

1. **F1 routing.** Should `Vault__Diff._init_components` be made clone-mode-aware (via the `_derive_keys_for_directory` helper the 06/04 contract already mandates for pull/fetch), so `history show`/`diff` — and therefore A3 — work on read-only clones? This is the architecturally consistent fix and extends the read-only-clone contract to the diff path, but it touches the diff read path for **every** command, so it deserves a deliberate decision rather than an inline patch. If declined, the A3 read-only claim must be re-scoped to full/headless clones in the brief and docstrings.
2. **F2 policy.** For `--files/--patch/--json` without a range: thread `-n/--limit` through (truncate to last N), or reject the combination? Threading is friendlier but changes `commits_in_range`'s contract; rejecting is safe but removes a reasonable capability. Architect recommends **thread it through** (least surprising), but this is a UX call.
3. **F3 default-host policy.** Is it acceptable for `history show`/`diff` to contact the **default** API host when no remote is configured, or must on-demand fetch require an explicitly-configured remote? Architect recommends requiring a real remote (gate on `resolve_remote(...)['name'] != ''`).
