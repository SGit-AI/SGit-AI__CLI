# sgit threat model and risk register — v0.21.0

**Status:** living document, current-state. Written 2026-10-08 from a full security
review of the code base at the 0.21.0 release candidate (dev), now that sgit is used
in production by multi-agent teams. Updated 2026-10-09: TM-R02, R04, R05, R06 and
R25 fixed (with two bugs found on the way, TM-F09 and TM-F10).

**How it stays honest:** every row of the risk register (§6) that can be shown in
code has a test. `tests/security/` runs in CI as its own job ("Run Security &
Adversarial Tests", 48 tests in ~2 s, in parallel with the other post-unit jobs) and gates a
release like every other job:

| File | What it proves |
|---|---|
| `tests/security/test_Security__Known_Gaps.py` | each **accepted / by-design** gap still behaves as this page says. The test performs the attack and asserts it **works**. A failure means a gap closed or moved: move the test to a `Fixed` file, inverted, and update the row here in the same commit. |
| `tests/security/test_Security__Fixed__*.py` | each **fixed** attack now fails. Run against the pre-fix sources, 27 of these 29 tests fail; the other 2 are controls that check legitimate use still works (fsck repair with the real bytes, an in-tree symlink). |
| `tests/integration/test_Security__Server_Boundary__Integration.py` | on the **real** server: a reader without the write key cannot move a ref (plain write, batch write, batch compare-and-swap), delete or add objects. That boundary is what keeps the read-key-holder rows below conditional on a hostile host. |
| `tests/_helpers/vault_adversary.py` | the attacker as a fixture: holds the read key only and writes straight into the host's store. |

## 1. What sgit is, in security terms

A vault is a content-addressed store of AES-256-GCM objects (blobs, trees, commits,
tags) plus a few mutable encrypted files (branch refs, the branch index, public
keys), kept on a host (SG/Send Transfer API, or a static site) and cloned to disk.

```
vault key  =  passphrase : vault_id
   ├── PBKDF2-SHA256 (600k) ──► read key   (AES-256-GCM: every object, ref, index, key file)
   └── PBKDF2-SHA256 (600k) ──► write key  (bearer header the HOST checks; no cryptographic role)

object id  =  obj-cas-imm-<sha256(ciphertext)[:12 | 32]>     (12 hex on format 1, 32 on format 2)
commit     =  ECDSA P-256 signature by the writing clone's key (author_key_id → bare/keys/<id>)
```

**The one fact everything else follows from.** The read key is symmetric (AES-256-GCM):
whoever can decrypt can also encrypt, so a read-key holder can produce objects, refs,
index entries and key files that every client accepts as genuine. A read-key holder
cannot derive the write key (both come from the passphrase with different salts, and
a read-only share never sees the passphrase), but the write key is only a header the
host compares: no client checks anything against it. The write key is an
authorisation the honest host enforces, not a cryptographic guarantee; anyone who can
write to the store without that check (the host, someone who compromised it, a static
mirror) and holds the read key can author any history. TM-R01.

## 2. Assets

| Asset | Where it lives | Who must not get it |
|---|---|---|
| File content, names, history | host (encrypted), clones (plain) | host, network, anyone without the read key |
| Integrity of history (what HEAD is, who wrote it) | refs + index on the host, commits | host, read-only holders, network |
| Vault key / read key | `.sg_vault/local/vault_key` (0600), `clone_mode.json` (read-only clones), backups, argv | other local users, the host, logs |
| Write key / access token | derived in memory; token store | read-only holders |
| Clone signing keys (private) | `.sg_vault/local/*.pem` (0600) | everyone but that clone |
| Named-branch signing key (private) | no longer stored (since 10/09); vaults created earlier keep one in `bare/keys/` until moved (TM-R27) | read-only holders |
| The user's machine | working copy, `.git/`, home directory | vault authors, the host |

## 3. Actors

| # | Actor | Holds | Can |
|---|---|---|---|
| A1 | **Host** — SG/Send operator, its cloud, anyone who compromises it, a static mirror | ciphertext, metadata, the write-key check | serve any bytes, withhold, replay, reorder; see sizes, timing, ids |
| A2 | **Network** — MITM, proxy | traffic | same as A1 on `http://`; on `https://` only metadata |
| A3 | **Read-key holder** — read-only share, published vault reader, ex-teammate who kept the read key | read key | read everything, ever; mint keys that decrypt; with A1's help, write |
| A4 | **Teammate** — full vault key | read + write key | everything A3 can, plus write through the host |
| A5 | **Hostile vault author** — a vault someone shares with you | full control of its content and names | choose paths, sizes, tree shapes, tags |
| A6 | **Local user / process** on the same machine | filesystem access per Unix permissions | read world-readable files, plant files and symlinks in the working copy |
| A7 | **Supply chain** — PyPI, dependencies, CI actions | the code you run | everything |
| A8 | **Other clients** — web UI, older sgit | their own policy | ignore client-side policy (format gate, signatures-required) |

## 4. Trust boundaries

```
 user machine                         │  host (untrusted for integrity & confidentiality)
 ┌──────────────────────────────┐     │   ┌──────────────────────────────────────┐
 │ working copy  ◄─ path guard ─┼─────┼───┤ objects  (content-addressed: checked) │
 │ .sg_vault/local (0600 keys)  │     │   │ refs, index, keys (mutable: NOT       │
 │ .sg_vault/bare  ◄─ verify ───┼─────┼───┤   bound to anything but the read key) │
 └──────────────────────────────┘     │   │ write-key check (the only write gate) │
        ▲ argv, env, backups          │   └──────────────────────────────────────┘
        │                             │
   local users (A6)            network (A2) — TLS when https://
```

The two lines that matter: **objects are self-verifying, mutable files are not**;
and **the write key is a host-side check, not a cryptographic one**.

## 5. Security mechanisms — what each one guarantees, and what it does not

| Mechanism | Guarantees | Does not guarantee |
|---|---|---|
| AES-256-GCM under the read key | confidentiality and integrity of every object, ref, index and key file against anyone without the read key | anything against a read-key holder; hiding sizes (TM-R08) or which objects change |
| Content addressing + verify-before-write (`Vault__Verified_Write`) | the host cannot substitute an object: bytes must hash to their id. **0.21: now on every download path** — clone, pull, fetch, sparse fetch/cat, fsck --repair, move auto-repair, cache pointer, large blobs via presigned URL | freshness for a fresh clone: the host can serve an OLD but authentic ref (SP-2; existing clones refuse a rewind); collisions at 48 bits (TM-R07) |
| Commit signatures (ECDSA P-256) | a commit was signed by a key whose file decrypts under the read key | **who** that is: any read-key holder can mint such a key (TM-R01) |
| `signatures-required` feature | pull and **clone** (since 10/09) refuse unsigned / bad / no-key commits made since the policy was switched on (`signed-since-<head>` records that point; older history is never held against anyone) | self-signed forgeries pass (TM-R01); other clients ignore it (A8); a vault that switched it on before 0.21 has no recorded start, so clone checks its head only |
| Rewind guard (`last_remote_head`) | writable **and read-only** (since 10/09) clones refuse a host that moves a branch backwards (`--accept-rewind` to override) | a fresh clone has nothing to compare with |
| Push compare-and-swap | **0.21:** a push that loses a race fails loudly and never overwrites the winner (in-memory and live per-op conflict) | — |
| Format gate (`format`, `min_client`, features) | a clone that has seen the gate keeps it (merge never lowers it) | a fresh clone takes whatever index the host serves |
| Path guard (`Vault__Path_Guard`) | vault data never writes outside the tree or into `.git` / `.sg_vault` (all spellings: case, 8.3, NTFS streams, ignorable code points). **0.21: every write/delete loop** (revert, branch switch, stash pop, sparse, restore, delete-on-pull), **resolved symlinks**, and **`.vault__*.zip` backups** | — |
| Working-copy scan | **0.21:** never reads through a symlink that leaves the tree | in-tree symlinks are followed (content duplicated) |
| File modes | **0.21:** every key-bearing file is created 0600 (vault key, bare-checkout key, backup zip with key, secrets store, PEMs, workflow step state via `mkstemp`) | directories are 0755 (names visible) |
| Hermetic tests | unit and security suites cannot reach the network | — |

## 6. Risk register

Classes: **By design** (a consequence of the architecture; changing it is a
redesign) · **Accepted** (known, not fixing short-term, documented) · **Fix soon**
(recommended next; cheap or high value) · **Fixed in 0.21**.
Likelihood/impact: H/M/L for a production team vault on the SG/Send host.

### 6.1 Fixed in 0.21.0 (this review and the earlier 0.21 work)

| ID | Risk | Actor | Fix | Evidence |
|---|---|---|---|---|
| TM-F01 | Host substitutes bytes on the paths that skipped the content-address check: `fsck --repair`, `vault move` auto-repair (the substitution was re-encrypted into the new vault — laundered, hashing correctly forever), sparse fetch/cat, cache pointer | A1 | verify-before-write everywhere; sparse raises `Vault__Integrity_Error` | `Fixed__Host_Substitution` (3 tests); `test_Vault__Sync__Sparse__Coverage2` |
| TM-F02 | **Clone checks out a HEAD with a file missing** (withheld, or refused as substituted) with only a warning. The working copy then reads as that file deleted, and the next commit deletes it from the vault for everyone. Pull already refused | A1 | clone refuses (`clone incomplete`), no key written, directory unusable | `Fixed__Host_Substitution` (2 tests) |
| TM-F03 | Hostile paths (`.git/hooks/*`, `.sg_vault/local/vault_key`, `../x`) written by revert, branch switch, stash pop, sparse fetch, restore; deletes outside the tree on pull; planted `.vault__*.zip` (which `init --restore` would restore) and `extractall` of a planted backup | A5, A3+A1 | guard on every loop; `.vault__*.zip` structural; restore extracts store members only | `Fixed__Hostile_Paths` (6 tests) |
| TM-F04 | Symlinks: a link to `~/.ssh/id_rsa` in the tree was committed and pushed (content of the target); writes through a symlinked folder left the tree; `secure_unlink` zero-filled the link **target** | A6, user error | scan skips out-of-tree links; `safe_join` checks the resolved path; unlink removes the link only | `Fixed__Symlinks_And_Local` (4 tests) |

| TM-F07 | Presigned URLs from the host followed with any scheme (`file://`, `ftp://`, internal `http://`) and no timeout | A1 | https, or http to loopback only; timeout 300 s; bytes still verified | `Fixed__Host_Substitution` (12 cases) |
| TM-F08 | Concurrent pushes: the loser reported success and/or overwrote the winner (live server reports a CAS miss as HTTP 200 with a per-op `conflict`) | A4 race | per-op conflict checked; refs written last; individual-write fallback pre-checks CAS | `tests/unit/review/test_Push__Concurrent_CAS.py` |

| TM-R04 → fixed | Clone ignored `signatures-required`: a newcomer cloned an unsigned head without a word | A3 + A1 | new clone step `verify-signatures` (before any branch is registered or file written) checks every commit since the recorded policy start, down to the shallow boundary | `Fixed__Trust_And_Policy` (2 tests) |
| TM-R05 → fixed | A read-only clone followed a host rollback silently | A1 | the writable clone's rewind guard on the read-only pull; `--accept-rewind` passes through | `Fixed__Trust_And_Policy` (2 tests, one a control) |
| TM-R06 → fixed | Tags: a far-future entry or tombstone pinned a name forever; `resolve` (tag names in `history reset`, `HEAD~` shorthand…) followed unverified entries | A3 + A1, A4 | an entry dated beyond now + 24 h loses to every entry that is not; `resolve` refuses a tag that is not *verified*, by name | `Fixed__Trust_And_Policy` (3 tests) |

### 6.2 By design

| ID | Risk | Actor | L / I | Mechanism / mitigation today | Evidence |
|---|---|---|---|---|---|
| **TM-R01** | **A read-key holder with write access to the store can author history every clone accepts and `check verify` calls *verified*** — the write key has no cryptographic role, and a signing key is trusted because its file decrypts under the read key. `signatures-required` stops an *unsigned* forgery, not a self-signed one. Read-key holders include every read-only share. | A3 + A1 | M / H | the honest host's write-key check (proven on the real server); team members are trusted | `Known_Gaps` TM-R01 (2 tests); `Security__Server_Boundary` |
| TM-R08 | Metadata visible to the host: exact plaintext size per file (GCM adds 28 bytes, no padding), number of objects, which objects change and when, team size (clone branches, keys), vault id. Deterministic tree encryption leaks equality (KI-SEC-02) | A1, A2 | H / L–M | none; content and names stay encrypted | `Known_Gaps` TM-R08 |
| TM-R12 | Read access cannot be revoked: a read key reads all history forever; `rekey` makes a new vault and leaves the old one readable on the host until deleted | A3 | M / M | delete the old vault after rekey | analysis |
| TM-R13 | The write key is a bearer secret: whoever has it can delete or rewrite everything on the host | A4 | L / H | clones and backups are the recovery path; rewind guard tells clones | analysis |
| TM-R26 | Client-side policy (format gate, `signatures-required`) is not enforced by other clients (web UI, old sgit) | A8 | M / M | `min_client` keeps old sgit out of writes | analysis |

## 9. Keeping this current

- A new security fix lands with a `tests/security/test_Security__Fixed__*` test and a
  TM-F row.
- A gap we decide to live with lands with a `Known_Gaps` test and a TM-R row
  (class, likelihood/impact, why).
- When a `Known_Gaps` test fails in CI, a gap closed or moved: do not "fix the test"
  without updating its row.
