# Addendum — Per-Commit Bundles: Measured

**Amends:** `v0__response__static-clone-proposal.md` §4 (publish-side performance)
**Date:** 2026-08-17 · **From:** sgit CLI team
**Question asked:** *bundle by commit — they're immutable, cacheable, and there are far
fewer commits than files. And once you've downloaded a zip per commit, don't you have
everything needed to rebuild `bare/` locally?*

**Short answer: yes — with one fork that decides the whole design, and three things
the commit bundles do not contain.** All numbers below are measured, not estimated
(10 commits × 20 files + churn, 292 objects / 576 KB).

---

## 1. The fork: snapshot vs delta

A "bundle for commit N" can mean two very different things:

| | contents | total across all commits | verdict |
|---|---|---|---|
| **Snapshot** | everything reachable from commit N | **1307 KB — 2.3× the store** | wasteful: unchanged blobs re-shipped in every bundle |
| **Delta** | only what commit N *introduces* | **576 KB — 1.0× the store** | correct: zero duplication, because CAS means an object is introduced exactly once |

Delta is the right unit, and the intuition behind the question is exactly right:
content-addressing already guarantees each object appears once, so per-commit deltas
partition the store with no overlap.

## 2. "Download every commit bundle and you can rebuild `bare/`" — verified true, with a catch

Union of all per-commit deltas **== every object in `bare/data/`**. Confirmed by
reconstruction. The catch is how you enumerate the commits:

> Enumerating by "the commits I know about" **missed 2 objects**: the empty root
> trees from the `init` commit. Walking the **parent chain from the head** covers
> everything (`full == on-disk` ✅).

So the publish step must enumerate commits by walking parents from the head, not from
a log of what was committed. This is the same shape as the proposal's own noted gotcha
about the init commit — it bites here too.

## 3. Three things commit bundles do **not** contain

Commit bundles reconstruct `bare/data/` only. Also required, and none of it is
reachable from any commit:

```
bare/refs/     2 files,  138 B    <- MUTABLE. the head pointer; must stay loose
bare/indexes/  1 file,   686 B    <- branch index
bare/keys/     3 files,  782 B    <- branch signing public keys
```

~1.6 KB total. They must be published loose, and `refs/` **must** stay loose and
separately cacheable: it is the only mutable object in the vault, so it is both the
freshness signal and the thing a CDN must not cache hard. Bundle everything else,
never the ref.

## 4. The finding that reframes the default: most readers don't want history

```
whole store        : 576 KB (292 objects)
head snapshot alone: 236 KB (209 objects)   <- 41%
```

A reader who wants *the current content* — a site visitor, an agent reading a shared
vault, a CI job checking out the latest — needs **41% of the store**. Downloading all
commit deltas gives them 100% and the entire history they never asked for.

That argues for publishing **both**, and letting the reader choose:

- `bundles/<commit-id>.bundle` — delta, immutable, cache-forever. History, incremental pull.
- `bundles/head-<commit-id>.bundle` — snapshot of the head only. **The default for a
  fresh read-only clone.** Redundant with the deltas by design; that redundancy costs
  41% of one vault-size and buys the common case a single GET.

## 5. Where bundles decisively beat a single pack: incremental pull

This is the strongest argument for the per-commit shape, and it is why we now prefer
it over §4's single-pack suggestion in the main response:

```
two new commits arrive, reader already has the rest:
  per-commit deltas : 172 KB   (2 GETs; every earlier bundle still cached, forever)
  single full pack  : 576 KB   (whole pack re-downloaded — its name changed)
```

A single full-vault pack is keyed by head commit, so **every publish invalidates it
entirely**. Per-commit deltas are immutable *and* stable: a bundle fetched once is
never fetched again, by anyone, on any CDN edge. With `Cache-Control: immutable` and a
content-addressed name, this is as good as static caching gets.

## 6. One free efficiency: zip STORE, never DEFLATE

Vault objects are AES-GCM ciphertext, which is incompressible. Measured on the real
vault's objects:

```
DEFLATE : 14508 B (1.078× raw)  4.1 ms
STORE   : 14468 B (1.075× raw)  0.4 ms
raw     : 13454 B
```

DEFLATE makes the archive **bigger** and costs ~10× the CPU. Publish with
`ZIP_STORED`. (The ~7.5% overhead in both is zip entry headers — the price of a
universally-readable container, and worth paying: every language and the browser can
read zip, and a zip's central directory plus HTTP `Range` allows extracting one object
without downloading the whole archive.)

## 7. The manifest is not optional — it is what makes bundles parallel

Without a published commit list, per-commit bundles must be fetched **sequentially**:
you cannot know commit N−1's id until you have fetched and decrypted commit N. That
turns a parallel fan-out into a serial chain — worse than the loose-object fetch it
replaces.

So `manifest.json` must publish **the commit ids in order** (plus object→bundle
mapping). Then a client reads the ref (1 GET), reads the manifest (1 GET), and fetches
every needed bundle **in parallel**. The manifest is cheap and it is the difference
between bundles being a win and a regression.

Note it is a *hint*, never authority: a client that distrusts it can always fall back
to the parent walk over loose objects.

## 8. Proposed publish layout

```
bare/refs/<ref-id>                    loose, mutable, short cache TTL   (freshness)
bare/indexes/… bare/keys/…            loose, tiny
bare/data/<object-id>                 loose — ALWAYS the source of truth
bare/cache/…                          already shipped; 1-batch hot reads
manifest.json                         commit list (ordered) + object→bundle map
bundles/head-<commit-id>.zip          head snapshot — default for a fresh clone
bundles/<commit-id>.zip               per-commit delta — history + incremental pull
```

Invariants (unchanged from the main response, and non-negotiable):

- **Derived, never authoritative.** Loose objects remain truth. A missing, stale or
  corrupt bundle degrades to slower, never to wrong. Every reader can fall back.
- **Immutable naming.** Bundles keyed by commit id; never `latest.zip`.
- **Verifiable without trust.** Every object extracted from a bundle is checked against
  `sha256(ciphertext)[:12]` — a bad bundle fails verification and the client refetches
  loose. This is what makes it safe to publish bundles to hosts we don't control.
- **No new crypto.** A bundle is a container of already-encrypted objects. It reveals
  object count and sizes — which a directory-listing static host already reveals.

## 9. Recommended order

1. **Transport** (works today — spike passes).
2. **`manifest.json`** — cheap, restores listing, and is a prerequisite for §7.
3. **`bundles/head-<id>.zip`** — biggest single win for the dominant case (41% and 1 GET).
4. **Per-commit deltas** — history and incremental pull.

Steps 2–4 are publish-format decisions, so they belong in the same round as the
`openapi.json` question: all of it is "what the publish step emits", and all of it must
be regenerable from the loose objects alone.
