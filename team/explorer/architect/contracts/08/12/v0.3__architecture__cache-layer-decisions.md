## 0. One-paragraph summary

The cache layer is a new top-level `bare/cache/` namespace holding two kinds of derived, never-authoritative objects: **`bare/cache/value/*`** (an encrypted copy of a file's content) and **`bare/cache/pointer/*`** (an encrypted pointer to a `blob_id` or `tree_id` — the branch-index pattern applied per path). Objects are self-describing (each stores its own `path`, `kind`, policy, and the `commit_id` it reflects), so **the folder is the registry — there is no manifest**. Creation is command-driven by aware clients; a cheap post-ref reconcile phase in push keeps everything healed. No authoritative byte changes anywhere: the tree entry, blob, tree, and commit formats are untouched, which is what makes the design compatible with every past client.

## 1. Confirmed decisions

| # | Decision | Resolution |
|---|---|---|
| D1 | Storage layout | `bare/cache/value/{id}` and `bare/cache/pointer/{id}`. `bare/indexes/` stays reserved for the single branch index. |
| D2 | Id derivation domains | `sg-vault-v1:file-id:cache-value:{vault_id}:{path}` and `sg-vault-v1:file-id:cache-pointer:{vault_id}:{path}` — kind is part of the domain, so the two namespaces are fully independent and changing a path's kind is visibly a new object, never a mutation. |
| D3 | Object id prefix | `cch-pid-{snw|muw}-{HMAC(read_key, domain)[:12]}` — one family, grep-distinct from `idx-`/`ref-`/`obj-`. |
| D4 | One object per path | A path is cached as value **or** pointer, never both. Enforced by `cache repair`. |
| D5 | Registry model | **Folder-as-registry.** No manifest. Every object stores its own `path` (collision guard doubles as registry data), `kind`, `mutability`, and `commit_id`. `list_files('bare/cache/')` + `batch_read` + decrypt reconstructs every mapping. Full enumeration is an edge case (repair, generic readers) — never on the hot path. |
| D6 | Reconcile source | Push reconcile uses server-side `list_files('bare/cache/')` (one call, issued only when acting), not the local mirror — so entries created by other clients are healed too, and clone needs no cache awareness. |
| D7 | Move / rekey | `vault move` drops `bare/cache/` **deliberately** (every id and ciphertext derives from `read_key`, so a rekey invalidates the layer by construction — today's hardcoded copy list in `Step__Move__Build_Temp_Vault._copy_structure` already omits it by accident; make it documented behavior). Rebuild is repair's job. Same rule for cross-key restore. |
| D8 | Command surface | `sgit cache add <path> [--pointer|--value]`, `sgit cache rm <path>`, `sgit cache status`, `sgit cache repair`. Read fast path (`sgit cat`) later. |
| D9 | Object schema | Safe_*-typed, round-trip-tested: `schema` (`cache_value_v1` / `cache_pointer_v1`), `path`, `kind`, `mutability`, `commit_id`, `content_type`, `size`, then `value_b64` (value) or `blob_id|tree_id` + `content_hash` (pointer). Random IV always (`crypto.encrypt`), never `encrypt_deterministic`. |
| **D10** | **Write path (added post-v0.15.0)** | Cache objects are written **directly to their derived path**, following the ref / branch-index mutable-object pattern — **never** through `Vault__Object_Store.store()`/`store_raw()`. Those now raise `Vault__Object_Collision_Error` when an existing id holds different bytes (the 48-bit-ID hardening), and a cache object is exactly that shape: an HMAC-derived id whose content changes on every reconcile. Routing cache writes through the object store would fail on the second write to any cached path. See contract §5.1. |

## 2. What each party does (the split, corrected)

| Party | Responsibility |
|---|---|
| **SG/Send (storage + auth layer)** | **Nothing new — confirmed by the project lead, 2026-08-13.** SG/Send does write to vaults, but only as an efficient object store that also enforces access-key auth on writes. It holds no vault logic and, being zero-knowledge, never holds `read_key` — so it **cannot** compute cache ids or maintain cache objects even in principle. A cache write reaches it as an ordinary `write`/`delete` op to a `bare/cache/...` file_id via the existing batch endpoint. No change required. |
| **SG/Vault (the client with keys — the real integration)** | This is where the logic lives and where the brief is needed: compute ids from the vault key / `read_key`, read via the batched `{ref, cache}` fast path, and — when it writes vaults — create/update cache objects and run the reconcile so its writes do not leave drift. |
| **sgit (this repo)** | Same aware-writer obligation: command-driven creation plus the post-ref reconcile. Reference implementation of the derivation and schemas. |
| **Aware readers (SG/Vault, `sgit cat`, any `read_key` holder such as a read-only Lambda)** | Compute the id locally, batch `{ref, cache_id}` in one round trip, verify `path` and `commit_id`, fall back to the tree walk on miss/stale/collision. `read_key` alone is sufficient — see contract §4.2. |
| **Old / unaware clients** | Behave exactly as today. Their writes leave cache entries detectably stale; their deletes leave orphans; both are healed by the next aware push or `cache repair`. They can never corrupt the layer because nothing they read, rebuild, or write carries cache knowledge — verified in §3.1. |

**Value vs pointer mechanics, precisely:**
- A **value** cache is a copy of the file's *content*, freshly encrypted with a random IV inside the cache object — not a byte-copy of the blob object (which has its own IV and therefore different ciphertext).
- A **pointer** cache is the branch-index pattern per path: a small encrypted JSON at a client-computable id, containing an object id (`blob_id` for a file, `tree_id` for a folder/subtree) plus metadata.

## 3. Compatibility statement (the design's core property)

No authoritative object changes: `Schema__Object_Tree_Entry`, tree encryption, every `obj-cas-imm-*` id, the ref and commit formats, and all existing reads are untouched. The file and folder being cached carry **no marker of being cached** — so there is nothing for an old client to strip (the v0.2-proven failure of in-entry storage cannot occur).

Honest statement: **100% read/write compatible with all past clients, with detectable lag.** The worst case after a foreign write is stale-but-detectable (the stored `commit_id` lags the head; readers fall back to the tree walk); the worst case after a foreign delete is an orphan (removed by reconcile/repair). A wrong answer is never served.

### 3.1 Compatibility verified against v0.15.0, not assumed

The claim above rests on one load-bearing property: **no old-client operation may enumerate the vault and delete objects it does not recognise.** If GC, fsck, or push swept "unreferenced" server objects, old clients would *destroy* cache entries rather than ignore them, and the design would be unsafe rather than merely lossy. Audited at tag `v0.15.0`:

| Surface | Behaviour | Cache impact |
|---|---|---|
| `api.delete` call sites | Only explicit batch `DELETE` ops and whole-vault `delete_vault` | Never sweeps unknown ids ✅ |
| `list_files` consumers | `Vault__Dump` (read-only), `_is_first_push` / `_server_has_named_ref` (boolean probes), dev plugin + bare-list CLI (read-only) | No consumer enumerates then deletes ✅ |
| GC (`Vault__GC`, `Vault__Sync__GC_Ops`) | Entirely local — change packs under `bare/pending/`, blob copies into `bare/data/` | Never touches the server ✅ |
| fsck (`Vault__Sync__Fsck`) | Reads `bare/data/{obj-cas-imm-*}` only | Cache invisible ✅ (correct — cache objects are not CAS) |
| clone | Fetches by known id (index, refs, keys, reachable objects); never enumerates | Ignores `bare/cache/` ✅ |
| push | Uploads local objects; first push walks local `bare/` | No remote deletion ✅ |

**Conclusion:** old clients can neither read, update, nor destroy cache objects. The single behavioural consequence is drift — an old client that edits or deletes a cached path leaves its cache entry stale or orphaned, detectable via the recorded `commit_id`, never wrong thanks to reader fallback, and healed by the next aware push or `sgit cache repair`.

Two secondary observations from the same audit:

- **Ordering protects `_is_first_push`.** That probe treats a non-empty `bare/` as "not first push". Because cache objects are only ever written *after* a successful ref-CAS (content-first ordering, §3 of the write flow), `bare/` can never contain cache objects while lacking data — so the probe cannot be misled into skipping the bootstrap upload.
- **Cosmetic only:** any UI that lists raw vault files (SG/Vault included) will begin showing `cch-pid-*` entries it does not recognise. Worth pre-announcing so it is not reported as corruption.

## 4. v1 touch set (smaller than the v0 plan)

Clone and pull need **no changes**. The complete v1 implementation surface in this repo:

1. **Crypto:** `derive_cache_value_file_id` / `derive_cache_pointer_file_id` (new domains, D2) + interop test vectors.
2. **Schemas:** `Schema__Cache_Value`, `Schema__Cache_Pointer` (D9) + round-trip tests.
3. **Storage:** `bare/cache/value/`, `bare/cache/pointer/` in `Vault__Storage` + path helpers; `create_bare_structure` additions (absence tolerated everywhere — old vaults never grow the folder until first use).
4. **Push:** post-ref reconcile phase in `Vault__Sync__Push.push` — after the Phase B batch (the remote ref-CAS completes inside it at `Vault__Sync__Push.py:265`, not at the local `write_ref` on `:273`): if `list_files('bare/cache/')` is non-empty, diff each entry against the new head's flat map (already in memory from `:141`) → `{rewrite, delete}` batch. Empty cache → one list call → no-op. Extend `Schema__Push_State` so a crash mid-reconcile resumes.
5. **CLI:** the `sgit cache *` commands (D8), including `repair` (enumerate folder, verify against head, rewrite drift, remove orphans, enforce one-object-per-path).
6. **Move:** make the cache drop deliberate (D7).

Read fast path in sgit (`sgit cat`) and the SG/Send browser/API halves consume the same derivation + schemas against shared vectors — Phase 4 of the original plan, unchanged.

## 5. Side effects audited (against live code)

| Code path | Effect | Verdict |
|---|---|---|
| First push `_upload_bare_to_server` (`Vault__Sync__Push.py:411`, `os.walk`) | Uploads local cache objects verbatim with nested file_ids — free bootstrap | OK; add a round-trip test |
| `vault move` `_copy_structure` (hardcoded dir list) | Cache dropped on move — correct (rekey invalidates ids+ciphertexts) but currently accidental | Make deliberate (D7) |
| fsck (`Vault__Sync__Fsck`, reads `bare/data/` only) | Cache invisible — correct, cache objects are not CAS | `cache repair` is this layer's fsck |
| GC (`all_object_ids` filters `obj-cas-imm-`) | GC never touches cache; orphaned pointers may reference GC-deleted blobs → read fails → fallback (detectable) | Recommend repair alongside GC |
| tree-iv migration (rewrites commits) | `commit_id` markers go stale → detectable, heals on next push; pointers target blobs, unaffected | None |
| Clone | Fetches known ids only; local cache mirror stays empty — fine, reconcile uses server listing (D6) | None |
| Read-only clones | Can compute ids and read; cannot maintain (no write_key) | Consistent |
| Backup/restore | Same key → ids valid; cross-key restore must drop cache (D7 rule) | Document |
| Zero-knowledge | Server sees two folder names + per-kind counts/update frequency; ids were already opaque and unlinkable to paths | Acknowledge in contract |
| Generic reader kind-discovery | A reader that does not know a path's kind batches both candidate ids in one round trip (breadth, one extra op) | Acceptable; aware readers know by convention |

## 5.1 F5 answered — reconcile and repair cost, measured

Readiness-review F5 made the repair walk a Phase 3 **gate**: it is the recovery SLA, and the design said measure it rather than assume. Measured at v0.15.0 + Phase 3, in-memory API, synthetic vaults (20 directories, ~10 lines per file):

| vault files | declared caches | push (incl. reconcile) | `cache repair` (full walk) |
|---|---|---|---|
| 200 | 0 | ~0.3–0.6 s | 48 ms (0 checked) |
| 200 | 10 | 288 ms | 49 ms |
| 200 | 50 | 327 ms | 74 ms |
| 1 000 | 10 | 1 288 ms | 180 ms |
| 1 000 | 50 | 1 139 ms | 210 ms |
| 1 000 | 200 | 1 305 ms | **342 ms** |

**Conclusions.**

1. **Repair is sub-second at realistic sizes** — 342 ms for 1 000 files with 200 declared caches. The recovery path is cheap enough to run on demand without ceremony, which is what F5 needed to establish.
2. **The scaling driver is vault size, not cache count.** Repair cost roughly quadruples from 200 → 1 000 files at a fixed cache count, while going 10 → 200 caches at a fixed vault size adds far less. That is `flatten()` of the head tree dominating — exactly the uncached walk F5 flagged. If repair ever becomes slow it will be because the *vault* grew, not because the cache set did.
3. **The reconcile is in the noise inside push.** At 1 000 files push costs ~1.1–1.3 s whether 10 or 200 caches are reconciled; the commit/flatten work dominates. Note the 200-file/0-cache row is slower than the 10-cache row — that is first-run/PBKDF2-warm-up variance, not a signal, and is left in rather than cherry-picked.
4. **Implication for the deferred optimisation.** A `commit_id`-keyed flat-map cache (readiness-review F5's suggested fix) would attack the dominant term for both repair and push. Not needed at these sizes; revisit if vaults reach tens of thousands of files.

Reproduce with the benchmark shape in this section's commit message; it uses only the in-memory API and needs no server.
