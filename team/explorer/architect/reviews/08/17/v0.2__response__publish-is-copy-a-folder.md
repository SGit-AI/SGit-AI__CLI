## 2. **Open question "Are content-addressed identifiers keyed?" — settled: they are, in effect**

The brief reasons from a hypothesis: *"content-addressed identifiers are hashes computed
over plaintext while the stored bytes are ciphertext"*, and concludes that after a rekey
**content ids survive**, so a private fork of a public template would be detectable.

**Measured, and the hypothesis does not hold.** Object ids are
`obj-cas-imm-{sha256(CIPHERTEXT)[:12]}` — over ciphertext, not plaintext — and blob
encryption uses a **random IV** (`Vault__Crypto.encrypt`; only *tree* objects and metadata
use the deterministic variant). Three consequences, each verified:

| Test | Result |
|---|---|
| Two different vaults holding the **same document** | **zero shared object ids** |
| Same content added twice **within one vault** | **not deduped** — a second object |
| Object ids surviving a **rekey** | **0 of 8** — complete turnover |

```
vault A: obj-cas-imm-225c0ff13134, 414cd49507dd, aa3057e7ec66, c92822ab756e, fb1b482c7cf0
vault B: obj-cas-imm-2c30cf310714, 691413fb61d1, ab1517f2975a, b8706b160ae6, f801adf07f39
shared : NONE
```

**So:**
- **Key claim #12 should be struck.** Content-addressed identifiers do *not* survive a rekey.
- **The disclosure you were worried about does not exist.** A private vault forked from a
  public template reveals nothing about its origin through object ids. **No protocol change
  is needed** — the behaviour you would have chosen is the behaviour you already have.
- **The corollary is a real loss, and should be recorded as a decision rather than
  discovered later:** open question *"Can a fork show what it changed from its template?"* —
  **not by identifier comparison.** The same property that protects a private fork prevents
  cheap template-diffing. A fork that wants to show its delta must do it at the content
  level (clone both, diff plaintext), which needs both read keys.

### The related finding you will need for the bundle work

`Vault__Sub_Tree.encrypt_or_reuse_blob` reuses a blob only when **the same path** previously
held the same `content_hash`. There is no content-global dedup: the same file at two paths,
or in two vaults, is stored twice. That is what makes forks unlinkable — but it also means
`obj-cas-imm-` ("CAS") names a *content-addressed store over ciphertext*, not a
deduplicating one. Worth stating in the protocol doc so nobody sizes a template registry
assuming forks share storage. They share nothing.

## 3. The plaintext surface needs a mechanism, not just a convention

We strongly agree with naming it — this is the part of the design most likely to become a
disclosure bug, because it is the only place where "encrypted by default" is deliberately
inverted. Two requirements we would put in the protocol:

1. **Fixed names, never patterns.** If the publish step decides the plaintext surface by
   matching (say `*loader*.html` or a directory), then anyone who can write to the vault —
   a collaborator, a compromised agent — can move a file into the plaintext surface by
   naming it. An explicit allow-list of exact paths cannot be manipulated from inside the
   vault's content.
2. **The published output must record what it exposed.** The manifest should list the
   plaintext files by name and hash, so "nothing else is exposed" is verifiable by
   inspection rather than by trust — which is the brief's own stated goal for the surface.

This is the same failure shape as the cache layer's silent-rewrite class: a default that
drifts, in a layer where nobody looks. Make it explicit, recorded, and diffable.

## 4. The filename convention lines up exactly with the key format we just shipped

Your convention — *"we're going to use the sgit underscore public underscore the actual read
key"* as the object **name** — matches, character for character, the prefix we agreed and
shipped today (commit `67c2ab6`):

```
sgit_public_read_<64-hex>          <- as a filename: the published key file
sgit_private_read_<64-hex>         <- never as a filename; fragment channel only
sgit_private_vault_<pass>:<id>     <- never published, ever
```

Three properties fall out for free:

- **The loader's discovery rule is a glob**: look for `sgit_public_read_*`. If absent, the
  vault is private and the fragment path applies. Exactly the constant-loader property the
  brief wants.
- **The public/private boundary is machine-checkable.** A publish step can refuse to emit
  any file whose name starts with `sgit_private_`, and a scanner rule `sgit_private_\S+`
  alerts on exactly the mistake ("a private key reached a published folder") while never
  firing on the intended `sgit_public_read_` filename. The convention and the leak alarm
  are the same mechanism, pointing opposite directions.
- **`sgit vault derive-keys` already emits the material**; `format_read_key(hex,
  public=True)` produces the published form, and `classify_key()` returns
  `Enum__Key_Kind.READ_PUBLIC` for it — so the loader has a reference implementation to
  mirror rather than a convention to re-derive.

One request for the site: it currently publishes the bare `c28b…:ivpijuvg`. Switching to
`sgit_public_read_c28b…` makes it self-describing and keeps the scanner story coherent.

## 5. Rekey-as-fork: agreed, with two operational facts

Agreed that this is the largest idea here, and §2 removes the objection to it. Two facts the
protocol section should carry, both measured earlier in this round:

- **A rekey republishes everything at new paths.** The vault_id changes and every object id
  changes, so a fork is not an incremental publish — it is a full new deployment. Fine for
  forks (that is the point); worth stating so nobody expects delta-publishing a fork.
- **On a git-hosted target, the original cannot be withdrawn.** Deleting the old objects
  leaves them in git history, clonable by anyone. For *public template* vaults this is
  irrelevant and even desirable. It matters only if someone publishes privately-intended
  content to a public repo first and forks later — worth one line, since the brief's trust
  model ("publishing a vault is publishing a repository") already accepts it.
